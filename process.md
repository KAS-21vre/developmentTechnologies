# Процесс командной работы — SkillSwap

## 1. Команда и зоны ответственности

Перед сдачей впишите реальные имена участников. Ответственный координирует свою область, но не обязательно выполняет всю работу самостоятельно.

| Роль | Зона ответственности |
|---|---|
| Product Owner / ответственный за требования | Приоритеты, формулировки требований, согласование MVP |
| Разработчик / ответственный за интеграцию | Структура репозитория, интеграция кода, техническая документация |
| Ответственный за качество | Критерии приёмки, тестовые сценарии и проверка результатов |
| Все участники | Ревью, обсуждение решений и актуальность документов |

**Состав команды:** заполнить.  
**Канал связи:** общий чат команды.  
**Хранилище:** общий Git-репозиторий.

## 2. Ритм работы

| Событие | Частота | Длительность | Цель |
|---|---|---:|---|
| Синхронизация | 2 раза в неделю | 10–15 минут | Прогресс, план и блокировки |
| Планирование | В начале недели | 20–30 минут | Выбрать приоритетные задачи |
| Ревью результата | В конце недели | 20–30 минут | Проверить результат и документацию |
| Ретроспектива | Раз в две недели | 15–20 минут | Выбрать одно улучшение процесса |

Доска задач: **Бэклог → Готово к работе → В работе → На проверке → Готово**. Команда старается завершать начатые задачи до начала новых.

## 3. Принятие решений
- Продуктовые решения обсуждаются командой, результат фиксирует ответственный за требования.
- При разногласиях варианты сравниваются по ценности для пользователя, трудоёмкости и риску.
- Изменения MVP, сроков и модели данных отражаются в документации и `CHANGELOG.md`.
- Нерешённые вопросы выносятся на консультацию преподавателю.

## 4. Definition of Ready (DoR)
Задачу можно брать в работу, если:
- [ ] описан ожидаемый результат;
- [ ] есть проверяемые критерии приёмки;
- [ ] известны зависимости и необходимые данные;
- [ ] задача достаточно мала для одной итерации;
- [ ] согласован приоритет.

## 5. Definition of Done (DoD)
Задача выполнена, если:
- [ ] результат соответствует критериям приёмки;
- [ ] изменения проверены другим участником;
- [ ] необходимые тесты пройдены;
- [ ] обработаны очевидные ошибочные ситуации;
- [ ] документация обновлена;
- [ ] результат проверен на согласованном окружении;
- [ ] изменение включено в основную ветку через запрос на слияние.

## 6. Инструменты

| Назначение | Инструмент | Правило |
|---|---|---|
| CJM и User Story Map | Miro | Экспортировать итоговую карту в PNG |
| Управление задачами | GitHub Projects, Jira или доска команды | У задачи есть ответственный и результат |
| Код | GitHub или другой Git-хостинг | Использовать ветки и запросы на слияние |
| Документация | Markdown в `docs/` | Обновлять вместе с требованиями |
| Связь | Общий чат | Важные решения переносить в документацию |

## 7. Приоритизация
MoSCoW: **Must** — обязательно для MVP; **Should** — важно, но можно отложить; **Could** — полезно при наличии времени; **Won't** — сознательно исключено из текущего объёма.

## 8. Журнал изменений
Изменения требований, MVP, приоритетов и сроков фиксируются в `CHANGELOG.md`. Документы пересматриваются после крупных этапов.
