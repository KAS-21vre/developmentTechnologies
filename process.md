# Процесс командной работы — SkillSwap

## 1. Команда и зоны ответственности

Перед сдачей проекта необходимо вписать реальные имена участников команды. Ответственный координирует свою область, но не обязательно выполняет всю работу самостоятельно.

| Роль                                        | Зона ответственности                                                |
| ------------------------------------------- | ------------------------------------------------------------------- |
| Product Owner / ответственный за требования | Приоритеты, формулировки требований, согласование MVP               |
| Разработчик / ответственный за интеграцию   | Структура репозитория, интеграция кода, техническая документация    |
| Ответственный за качество                   | Критерии приёмки, тестовые сценарии и проверка результатов          |
| Все участники                               | Ревью, обсуждение решений, тестирование и актуальность документации |

Роли в команде не следует путать с ролями пользователей SkillSwap. В самой платформе нет постоянного разделения на преподавателей и учеников: один пользователь может обучать в одном обмене и получать знания в другом.

## 2. Ритм работы

| Событие          | Частота          | Длительность | Цель                                               |
| ---------------- | ---------------- | -----------: | -------------------------------------------------- |
| Синхронизация    | 2 раза в неделю  |  10–15 минут | Обсуждение прогресса, планов и блокирующих проблем |
| Планирование     | В начале недели  |  20–30 минут | Выбор приоритетных задач                           |
| Ревью результата | В конце недели   |  20–30 минут | Проверка выполненных задач и документации          |
| Ретроспектива    | Раз в две недели |  15–20 минут | Определение одного улучшения процесса              |

Доска задач:

**Бэклог → Готово к работе → В работе → На проверке → Готово**

У каждой задачи должны быть ответственный, описание ожидаемого результата и критерии приёмки. Команда старается завершать начатые задачи до начала новых.

## 3. Принятие решений

- Продуктовые и технические решения обсуждаются командой, а их результаты фиксируются ответственными участниками.
- При разногласиях варианты сравниваются по ценности для пользователя, трудоёмкости реализации и возможным рискам.
- Изменения MVP, сроков, требований и модели данных отражаются в соответствующей документации и `CHANGELOG.md`.
- Новые функции оцениваются с учётом их соответствия концепции SkillSwap — обмену знаниями и навыками без обязательной денежной оплаты.
- Нерешённые вопросы, влияющие на объём или направление проекта, выносятся на консультацию преподавателю.

## 4. Definition of Ready (DoR)

Задачу можно брать в работу, если:

- [ ] Описан ожидаемый результат.
- [ ] Определены проверяемые критерии приёмки.
- [ ] Известны зависимости и необходимые данные.
- [ ] Задача достаточно мала для выполнения за одну итерацию.
- [ ] Согласован приоритет задачи.
- [ ] При необходимости определены связанные требования и документы.

## 5. Definition of Done (DoD)

Задача считается выполненной, если:

- [ ] Результат соответствует критериям приёмки.
- [ ] Изменения проверены другим участником команды.
- [ ] Необходимые тесты пройдены.
- [ ] Обработаны очевидные ошибочные ситуации.
- [ ] Документация обновлена.
- [ ] Результат проверен на согласованном окружении.
- [ ] Изменение включено в основную ветку через запрос на слияние, если используется соответствующий процесс Git.

Для функциональности обмена навыками дополнительно проверяется корректность полного сценария:

- [ ] Пользователь может опубликовать предложение об обучении или запрос на получение знаний.
- [ ] Другой пользователь может найти публикацию и отправить предложение или отклик.
- [ ] Участники могут согласовать условия обмена, дату, время и формат занятия.
- [ ] Согласование времени не приводит автоматически к завершению обмена.
- [ ] После проведения занятия оба участника могут подтвердить его выполнение.
- [ ] Обмен получает статус завершённого только после подтверждения обеими сторонами.
- [ ] После завершения обмена оба участника могут оставить отзыв.

## 7. Приоритизация

Для определения очередности реализации используется метод MoSCoW:

- **Must** — обязательные функции, без которых невозможно реализовать основной сценарий MVP.
- **Should** — важные функции, которые желательно реализовать, но допускается перенести.
- **Could** — дополнительные улучшения, реализуемые при наличии времени.
- **Won't** — функции, сознательно исключённые из текущего объёма проекта.

Приоритеты определяются с учётом основной цели SkillSwap — обеспечить полноценный обмен навыками между пользователями.

В первую очередь реализуются регистрация и профили, публикация предложений и запросов, поиск партнёров, согласование условий, подтверждение проведённого занятия, отзывы и базовая модерация.

## 8. Журнал изменений

Изменения требований, состава MVP, приоритетов и сроков фиксируются в `CHANGELOG.md`.

Документы проекта пересматриваются после крупных этапов разработки. При изменении функциональности проверяется согласованность требований, User Story Map, Customer Journey Map, дорожной карты, плана работ и описания процессов.

Все участники команды отвечают за актуальность документации в пределах своих задач.


## Использование AI-инструментов в ЛР 2Б, 2В и 2Г

### ЛР 2Б — проверка ограниченных контекстов по Event Storming

**Запрос к модели:**
> На основе списка событий SkillSwap выдели ограниченные контексты. Не группируй события только по таблицам или существительным. Для каждого контекста укажи его ответственность, ключевые события и возможные границы согласованности. Отдельно перечисли сомнительные места.

**Кандидат модели:** Identity (регистрация и профиль), Catalog (навыки и публикации), Exchange (предложения, условия, проведение занятия и подтверждение), Reputation (отзывы и рейтинг), Moderation (жалобы и решения).

**Сопоставление с проектной моделью:** названия и основные обязанности совпадают с контекстами, зафиксированными в `docs/domain/context-map.mmd` и `docs/domain/aggregates.md`. Важное уточнение: регистрация/профиль не должны автоматически включать каталог навыков; отзыв и рейтинг не должны завершать обмен; модерация не должна изменять историю обмена напрямую.

| Вопрос методички | Результат анализа |
|---|---|
| Модель разделила по сущностям вместо границ модели? | В целом нет: предложены контексты по ответственности. Однако совпадение названий ещё не доказывает правильность границ. |
| Какие события объединены/разделены иначе? | События согласования условий, планирования занятия и двухстороннего подтверждения логично оставить в Exchange; публикацию отзыва — в Reputation. |
| Какие правила названы инвариантами ошибочно? | Нельзя считать «пользователь может оставить отзыв» инвариантом агрегата Exchange: это правило перехода между контекстами, зависящее от завершённого обмена. |

**Ограничение:** в архиве находится проектная расшифровка Event Storming, а не подтверждение проведённой командной сессии. Команда должна сверить результат с реальной доской и приложить фото `docs/domain/event-storming.jpg`. Поля о фактических разногласиях участников заполняются после обсуждения, а не восстанавливаются по ответу AI.

### ЛР 2В — сравнение архитектурных стилей

**Полный запрос к модели:**
> SkillSwap — учебная веб-платформа обмена навыками. В MVP есть профили, каталог навыков, публикации «могу научить» и «хочу научиться», поиск, предложения обмена, согласование условий и времени, подтверждение проведения обеими сторонами, отзывы и модерация жалоб. Команда небольшая, срок ограничен семестром; требуется серверная проверка прав, тестируемость бизнес-правил и единая согласованная модель обмена. Предложи архитектурный стиль, объясни плюсы, минусы, цену выбора и условия пересмотра. Не предлагай микросервисы без обоснования.

**Ответ модели в кратком виде:** модульный монолит с явными границами доменных модулей. Это позволяет разделить Identity, Catalog, Exchange, Reputation и Moderation без сетевой сложности и независимого развертывания микросервисов.

**Контрольный вопрос без контекста:**
> Стоит ли использовать микросервисную архитектуру для веб-платформы?

**Сопоставление:** ответ без контекста перечисляет общие преимущества независимого масштабирования и развертывания, а также сетевые и эксплуатационные издержки. Он не учитывает размер команды, срок семестра и необходимость согласованного изменения состояния обмена. Ответ с контекстом рекомендует модульный монолит и называет цену: один релиз, единая БД и необходимость соблюдать границы модулей.

| Критерий | Ответ с контекстом | Ответ без контекста |
|---|---|---|
| Рекомендация | Модульный монолит | Общий перечень плюсов и минусов микросервисов |
| Учёт команды и срока | Учитывает небольшую учебную команду и семестр | Не учитывает |
| Согласованность обмена | Выделяет единый модуль Exchange | Не знает доменных правил |
| Цена решения | Один релиз, единая БД, правила границ модулей | Общие сетевые и эксплуатационные издержки |
| Условие пересмотра | Несколько независимых команд, разные профили нагрузки или потребность в независимых релизах | Не может назвать условие для конкретного проекта |

**Сравнение с ADR-0003:** рекомендация совпадает с выбранным в проекте стилем. AI полезен как проверка полноты аргументов, но не является автором принятого решения. Определяющий довод проекта — ограниченный срок и небольшая команда при необходимости сохранять границы предметных областей.

### ЛР 2Г — черновик C4 Container

**Описание, переданное модели (6 предложений):**
> SkillSwap — веб-платформа, в которой участники создают профиль и указывают навыки, которыми могут делиться или которые хотят освоить. Пользователь публикует предложение или запрос и ищет подходящие публикации других участников. После отправки предложения стороны согласуют условия, дату, время и формат занятия. Обмен считается завершённым только после подтверждения проведения занятия обеими сторонами. После завершения участники могут оставить отзывы, а модератор рассматривает жалобы. В MVP платформа не предоставляет видеосвязь, кошелёк и встроенную оплату.

**Черновой вывод модели:** браузерный клиент, REST API, реляционная база данных; как возможные внешние зависимости модель упомянула почтовый сервис и видеосвязь.

| Проверка | Вывод |
|---|---|
| Элементы на неверном уровне | Почтовый провайдер и видеосвязь — внешние системы/сервисы, а не внутренние контейнеры SkillSwap. |
| Связи без подписи или направления | Между клиентом и API нужно явно показать JSON/REST поверх HTTPS; между API и БД — SQL/TCP. |
| Лишние элементы | Встроенный видеосервис, платежи, кошелёк и отдельный брокер не входят в MVP и не должны появляться как внутренние контейнеры. |
| Что принято | Разделение браузерного клиента, серверного API и хранилища; внешний почтовый сервис показан только как будущая зависимость. |
| Что отклонено | Микросервисы, брокер сообщений, кеш и отдельный видеоконтейнер: для текущих требований они не обоснованы. |

**Важно:** C4 Container дополнена отдельным контейнером веб-сервера статических файлов, чтобы показать самостоятельную запускаемую часть. Это проектное архитектурное уточнение требует подтверждения и не означает, что сервер уже реализован.

**Статус записей:** приведённые запросы и аналитические сравнения подготовлены как черновик использования AI для проекта. Реальные даты запросов, участники командного обсуждения, принятые командой решения и фактические расхождения следует подтвердить и заполнить перед сдачей.
